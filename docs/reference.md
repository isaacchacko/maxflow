# maxflow reference

Local web terminal for agent work on this machine. A Bun server on `127.0.0.1:4747` runs commands in real PTYs (Bun's built-in `terminal` spawn, no native deps) and streams them to xterm.js in the browser. Every session runs inside tmux on a private socket (`tmux -L maxflow`, config in `tmux.conf`: no prefix, no status bar), so it outlives both the tab and the server: on startup maxflow adopts any `mf-*` tmux sessions, replays their history and reattaches. You can also reach one from a terminal with `tmux -L maxflow attach -t mf-<id>`.

```sh
bun server.ts                      # http://localhost:4747  (MAXFLOW_PORT to change)
./cli.ts new --name api -- bun dev # start a session, prints its link
./cli.ts chats [query]             # list Claude Code chats, newest first
./cli.ts resume <claude-session-id> [--safe] [--force]
./cli.ts ls
```

maxflow is an installable web app (`public/manifest.webmanifest`): in Chrome, open `http://localhost:4747` and choose Install (the icon at the right of the address bar) to get its own window, Dock icon and Launchpad entry.

## Driving from an agent

Everything the browser does is also an HTTP call, so an agent can run a session, type into it and read it back without a websocket:

```sh
id=$(./cli.ts new --name job -- claude); id=${id##*/}
./cli.ts wait $id --match 'trust this folder|❯'   # block until the prompt shows; prints the screen
./cli.ts keys $id Down Enter                      # tmux key names: Enter Escape C-c Up BTab ...
./cli.ts send $id 'fix the failing test'          # types the text, then Enter as a separate keystroke
./cli.ts wait $id --idle 5000 --timeout 600000    # quiet for 5s (claude's spinner counts as output)
./cli.ts screen $id --history 200                 # plain text, no escape codes
./cli.ts kill $id
```

`wait` prints the screen to stdout and its reason (`[match]`, `[idle]`, `[exited]`, `[timeout]`) to stderr, and exits 2 on timeout. The API underneath: `POST /api/sessions/:id/input {text?, keys?, enter?}`, `GET /api/sessions/:id/screen?history=N`, `GET /api/sessions/:id/wait?match=RE&idle=MS&timeout=MS`, `PATCH /api/sessions/:id {name?, archived?}`. After a session ends, `screen` returns the last capture.

## What agents are told

Every session's shell carries `MAXFLOW_SESSION=<id>`. A `SessionStart` hook in `~/.claude/settings.json` runs `hooks/claude-intro.sh` whenever claude starts, resumes, clears or compacts with that variable set, and puts `GET /api/sessions/:id/intro` into its context: what maxflow is, the agent's own id and name, how to rename, message other sessions, subscribe to events and wait (`cli.ts wait <kind>:<ref>` to sleep on one thing, `wait done` when finished; never archive itself), and what each running sentry does for it (the same text the graph's sentry edges send). Edit `intro()` in `server.ts` to change it.

## Events and sentries

maxflow has a small event bus (`~/.maxflow/events.jsonl`). Topics are `/`-separated; `*` matches one segment, `**` any number.

```sh
./cli.ts sub 'gh/dryft-ai/app/pr/7031/ci'          # block until the next matching event, print it as JSON
./cli.ts sub 'gh/**' --follow                       # stream
./cli.ts pub some/topic '{"any":"json"}'
./cli.ts notify <id> 'text'                         # typed into the session once it is idle at an empty claude prompt
```

Sentries are sessions the server starts on boot (`MAXFLOW_SENTRIES=0` to skip) and tmux keeps across restarts.

**gh** (`sentries/gh.ts`) runs one GraphQL poll per repo every 30s, covering every PR a live session is tied to. A session is tied to a PR when its cwd has the PR's branch checked out, when it declared the PR with `~/.claude/set-pr.sh` (a bare number resolves against the repo of the PR links the session mentioned), or when it ran `./cli.ts gh watch <pr>` (which defaults to `$MAXFLOW_SESSION`). The sentry publishes `gh/<owner>/<repo>/pr/<n>/{opened,push,ci,review,comment,thread,decision,conflict,merged,closed}`. For CI finishing, reviews, comments, conflicts, merges and closes, it also notifies the tied sessions. The agents post as the gh user too, so a comment or review by that user is passed on only when no agent's tool call in a maxflow transcript carries its text: the user's own comments reach the tied sessions, the agents' own posts are never echoed back. It also watches the PRs the review sentry lists (`review-watch.json`). Each poll is kept whole in `gh-status.json`, so `./cli.ts gh status [pr]` answers what an agent would run `gh pr checks` or `gh pr view` for (CI with failed and pending checks, reviews, unresolved threads, latest comments) without calling GitHub; with no PR it covers every one the session is tied to, and a PR not polled in the last 2 minutes is fetched once and watched for the session. Every notice ends by naming that command. It draws an edge in the graph to each session it is tied to, labeled by its PRs (`gh-edges.json`). State lives in `~/.maxflow/gh-state.json` and `gh-watch.json`.

**slack** (`sentries/slack.ts`) polls Slack every 60s (`SLACK_SENTRY_INTERVAL`) through the `mcp` CLI's `claude.ai/slack` connector, so it needs no token of its own. A session is tied to a Slack thread when its agent posted there with the connector's `slack_send_message` (read from its transcript; the tie lasts 3 days past its last post there, `SLACK_POSTED_TIE_MS`), or when it ran `./cli.ts slack watch <ref>`, where `<ref>` is a message or thread permalink, a channel id or `#name` (its top-level posts), or anything else as a search query (`'from:<@U012ABCDEF>'`). The first look at a target only records where it stands; after that every new message is published as `slack/<channel>/<thread ts>/reply`, `slack/<channel>/message` or `slack/search`, and the tied sessions are notified, except of messages they posted themselves. Every mention of the user is published as `slack/mention` for anyone to `sub`, notifying nobody. Explicit watches end once every session they were for has. The last 50 messages of each target (and a thread's parent) are kept in `slack-messages.json`, so `./cli.ts slack read <ref> [--last N]` answers from them instead of the connector's read tools; a target not polled in the last 3 minutes is read once and watched for the session. Every notice ends by naming that command. It draws an edge in the graph to each session it is tied to, labeled by what it watches (`slack-edges.json`). State lives in `~/.maxflow/slack-state.json` and `slack-watch.json`.

**rename** (`sentries/rename.ts`) titles each session by the topic it owns (the ticket, PR or feature), never its status, so a title only changes when the topic does. A session gets its first title once 400 new characters have reached its screen, then a new one every 4000 (`RENAME_FIRST_CHARS`, `RENAME_EVERY_CHARS`). "New" means lines in the last 300 lines of screen that weren't there at the last rename, so spinner redraws don't count. Each title is one `claude -p --model haiku` call with no tools and no saved transcript, about 1.5s and $0.0001. Rename a session yourself and the sentry leaves it alone from then on.

**graph** (`sentries/graph.ts`) decides which URLs become nodes in the graph view. The server finds every URL a session mentions (an agent's own and its user's messages in the transcript, a shell's tmux history) and serves them with their surrounding text at `GET /api/links`. Every 15s the sentry judges each session's new ones in one `claude -p --model haiku` call, keeping only links meant to be opened (a PR or ticket, a deploy, a published page, a running dev server) and dropping incidental ones (code, docs, CDN, stack traces, maxflow itself). Each URL is judged once per session; verdicts live in `~/.maxflow/graph-links.json`, and a URL stays hidden until judged. It also groups the running sessions by the work they share (one haiku call whenever the set of sessions or their titles change, at most every 2 minutes, `GRAPH_GROUP_EVERY`) into `~/.maxflow/graph-groups.json`; the server serves each session's `group`, and the graph joins every pair in a group with a hidden link that pulls them together without being drawn. Sentries always share one group, `maxflow sentries`, and every session working on maxflow itself shares `maxflow development` (pinned when its title says maxflow or it runs in this repo, otherwise by haiku); the rest are titled like the rename sentry's session titles. Press `hg` in the graph view to outline each group and show its title; `ht` hides node titles but keeps the group titles. `G` acts on a whole group: it outlines and numbers them, `G<n>r` opens the new-agent draft as a router for group n, with every running member picked (so each is introduced to it) and a brief to coordinate them, ready to edit before it starts. A GitHub PR's node is colored by its state, polled every 30s: green open, purple merged, red closed (a lone PR drawn as its domain's node gets a ring in that color around the favicon). Right-click a link (or a domain node, for all its links) to archive it: it is greyed out everywhere it appears and hides along with archived sessions (`ha`). Archived URLs live in `~/.maxflow/archived-links.json`; `PATCH /api/links {urls, archived}` sets them. A domain node shows its site's favicon and a sentry's node an icon for what it watches (a PR for gh, # for slack, a tag for rename, a pulse for health, waypoints for graph); `@isaacchacko/graph` draws both inside the node, ringed in its color, so they dim, highlight and move with it.

**review** is a claude agent (`sentries/review.md` is its brief), the one place to see and drive the user's open PRs toward prod or closed. Its feed, `sentries/review.ts`, runs beside it in the same pane (logging to `~/.maxflow/review-feed.log`, exiting with the agent): every 2 minutes (`REVIEW_SENTRY_INTERVAL`) it stages each open PR of the user's (draft, conflict, ci failing, changes requested, ci running, needs reviewer, in review, approved, merging) with the sessions on it into `~/.maxflow/review-queue.json`, hands them all to the gh sentry in `review-watch.json`, and writes the PR-labeled graph edges to `review-edges.json`. It notifies the agent when a PR changes stage, and when a person's comment or review lands that no session heard (the gh sentry's events carry `who`, null for an agent's own post, and `told`, the sessions it notified). The agent delivers such a comment by resuming the chat that opened the PR (or starting one in a worktree), tying it to the PR and passing the comment on; it tells the user what to do next, revives sessions for failing PRs, flags PRs to close, and merges or closes only on the user's word in its terminal. It never requests reviewers.

**funnel** is a claude agent (`sentries/funnel.md` is its brief), the front door for the user's requests. Type a request into its pane and it finds the request's root (ticket, PR, bug, feature), matches it against the live sessions' titles, groups, links and screens, and delivers it verbatim: with `notify` to the agent already on that root, by resuming a finished chat that owned it, or to a new `claude` it starts in the right folder. It then runs `./cli.ts link <owner> <other> '<why>'` for each live agent whose context would help (same PR or ticket, same files or contract, an earlier diagnosis), which introduces the two as drawing an edge in the graph does, and reports in one line where the request went. It routes and never does the work itself.

**questions** (`sentries/questions.ts`) is the throttle on the user's attention: every question an agent wants to raise goes through it, never into a chat turn the agent ends. An agent runs `./cli.ts ask '<question, evidence, recommendation>'`, which returns at once so it can keep working. The server keeps the queue in `~/.maxflow/questions.json`; an agent holds at most one open question, and asking again adds to it. The sentry checks each new one with `claude -p --model sonnet` (`QUESTIONS_MODEL`) against the "Decisions that are Isaac's" rule it reads from `~/.claude/CLAUDE.md`: what the agent should decide itself goes back to it with the reason, the rest becomes pending. A failed check lets the question through, and `QUESTIONS_GATE=0` passes every one. The user answers or dismisses pending questions in the Questions panel (the sidebar's ? button, its count also in the tab title). The answer is typed into the agent's prompt, and the agent either continues or answers back with `./cli.ts ask --re <id> '...'`, which skips the gate. A bounced agent can force its question into the queue the same way. Events go out as `question/{asked,pending,answered,bounced,dismissed}/<id>`, and `./cli.ts questions [--all]` prints the queue.

**meta** is a claude agent (`sentries/meta.md`) that watches the other agents and owns the fleet getting faster and better; Isaac can talk to it in its pane ("what's our bottleneck?"). Its feed (`sentries/meta.ts`, logging to `~/.maxflow/meta-feed.log`) runs beside it: every 15 minutes (`META_INTERVAL`) it reads each live agent's transcript from where it last stopped (offsets in `~/.maxflow/meta-state.json`; a transcript seen for the first time from its last 2MB) and times the window: turns from prompt to the Stop hook's summary, each tool call from use to result, each model reply from its `api-request` to the answer, plus repeated identical commands. Turns and tool calls still running count only while the session is working. Agents over a threshold (a turn over 10 minutes, a tool call over 5, a reply over 3, a command run 4+ times; `META_SLOW_TURN_MS`, `META_SLOW_TOOL_MS`, `META_SLOW_MODEL_MS`, `META_REPEATS`) go to the agent as a `[maxflow meta]` notice, with full digests in `~/.maxflow/meta-flagged.json`. The agent reads their screens, separates stuck from busy, messages each slow one the cause and a fix, logs what it told whom in `~/.maxflow/meta-notes.md` so repeats get called out, and keeps up to 8 lessons in `~/.maxflow/meta-lessons.json` that every new agent's intro lists.

**assistant** is a claude agent (`sentries/assistant.md`), the user's personal assistant and the keeper of his task board, which ⌘K opens over the terminal (or `/#tasks`). He never makes or moves a task himself: the agent derives each one from what he asks for, reading between the lines of his prompts, and moves it through `todo`, `doing`, `you` (waits on him), `waiting` (on CI, a review or another agent), `done` and `dropped` as the agents work. A task whose root is a question carries its answer. Clicking a card shows its timeline: one line per step toward done, with the session that took it. Its feed (`sentries/assistant.ts`, logging to `~/.maxflow/assistant-feed.log`) runs beside it: every 10 minutes (`ASSISTANT_INTERVAL`) it reads each agent's transcript from where it last stopped (`~/.maxflow/assistant-state.json`; the first read reaches back a day, `ASSISTANT_BACKFILL_MS`) for the user's own prompts (any the server didn't stamp with a sender, plus funnel relays stamped verified) and the reply each agent ended its turn on, takes the bus's question, wait and PR events, and notifies the agent with one digest (whole in `~/.maxflow/assistant-digest.json`). The server keeps the board in `~/.maxflow/tasks.json` behind `GET /api/tasks` and `POST /api/tasks[/<id>] {title?, kind?, status?, answer?, session?, link?, event?, at?}`; the agent writes it with `./cli.ts task new <title>` and `./cli.ts task <id> --status ... --event ...`, and `./cli.ts tasks [--all]` prints it. Two parts of the board come straight from the other sentries instead: **Needs you** opens with a collapsible card of the PRs the review sentry stages `needs reviewer`, and **Your open comments** lists the user's own PR comments not yet resolved (`GET /api/comments`). The server keeps every comment the gh sentry's `who` marks as his, not an agent posting as him, in `~/.maxflow/user-comments.json` (on first boot seeded from the whole event log), and checks each against the last poll: a review-thread comment is open until its thread is resolved, a top-level one until a person or agent comments after it (CI bots don't count), and both close once the PR is merged or closed.

**inbox** (`sentries/inbox.ts`) catches what reaches the user that no session heard, in plain code with no model turn. The slack sentry searches every minute for mentions of him (`slack/mention`), DMs to him (`slack/dm`, from `to:<@him>`) and his own posts (`slack/own`, from `from:<@him>`). Each thread he posts in himself, not through an agent, stays watched by nobody for 2 days (`SLACK_OWN_TIE_MS`) and is reread at most every 5 minutes (`SLACK_OWN_READ_MS`), so its replies are published too. Inbox skips agents' posts, anything a session was told about, and bots except when they mention him. A bot's mention ("a run on main is red") is one task per kind of alert, named by its text without links and numbers: repeats add a note at most hourly, and the funnel hears of a kind once per open task. It makes or adds to one board task per thread or DM, hands a thread reply to the chat that once posted there (found by grepping transcripts, revived with `resume`), and sends unowned mentions and DMs to the funnel in 3-minute batches. Every 5 minutes it searches GitHub for open PRs requesting his review or assigned to him, makes a "Review …" task for each, and writes them to `~/.maxflow/inbox-watch.json`, which the gh sentry watches alongside the review queue. A new request on a PR over 800 changed lines, or one touching migrations, ERP/SAP, infra, workflows or auth, gets a review agent (at most 2 at once) in a detached worktree, briefed to make no GitHub or Slack writes. Comments and reviews no session heard go onto the PR's task; his own PRs are the review sentry's, so there it only adds to a task that exists. A CI failure on his PR whose failed checks all match `~/.maxflow/flaky-checks.json` (a JSON array of regexes) is re-run once per commit. Every 15 minutes it raises stalls as task events, never pings: a review request 24h+ old, a PR requesting his review that has been idle 3+ days, and a Slack question to him with no post of his in that thread or DM after 3h. Every task it touches is published as `inbox/task` or `inbox/update` for the assistant.

**ram** (`sentries/ram.ts`) keeps agents from running CI's work on this machine. Every 15s (`RAM_INTERVAL`) it lists processes and finds the test runners, typecheckers, linters and builds (vitest, jest, pytest, mypy, eslint, `pnpm test`, `next build` and the like) whose process tree leads up to a live agent's tmux pane. Dev servers such as storybook are left alone. It sums each job's memory from its topmost such process down, so a `pnpm exec` wrapper counts with the runner it started. A job over 1.5% of physical RAM (`RAM_MAX_PCT`) gets SIGTERM, then SIGKILL after 3s. The agent is then notified to commit and push so the job runs on the Blacksmith CI runners, and to read the result with `gh pr checks`. Each kill is published as `ram/killed/<session>`. `RAM_DRY=1` logs what it would kill without killing.

**health** (`sentries/health.ts`) polls the server every second. Sentries live in tmux, so this one keeps running while the server is down. Once the port has been refused for 3s while the launchd agent is still loaded, the sentry binds the port itself and serves an "Oh no!" page (`sentries/health.html`), so open tabs reload into it instead of erroring. The page shows how long the server has been down and what launchd reports. If the server still isn't back 45s later (`HEALTH_DOWN_MS`), the sentry starts a `maxflow recovery` session straight in tmux: `claude` in bypass mode, primed with launchd's status and the tail of `/tmp/maxflow.log`, told to fix the cause, kickstart the agent and confirm it answers. That session's terminal appears live on the page, like switching to tty2 when the desktop is down, and you can type to it. On boot the server asks the page to hand the port back (`POST /__down/release`) before binding. That request restarts the agent's 45s clock, because a normal restart spends about 20s adopting sessions first. The sentry then stays off the port for 15s while the server binds, and the page sends you to the recovery session in the real UI. One agent at a time, at most one per 15 minutes (`HEALTH_COOLDOWN_MS`). Unloading the launchd agent counts as down on purpose: no page, no agent.

The API can answer while the UI is broken: Bun hot reload rebuilds on every save, so an agent caught mid-edit (a file cut off, an import of a file not written yet) leaves `/` answering 500 "Build Failed". The sentry checks `/` every 5s and, if the build has stayed broken for 60s (`HEALTH_BUILD_DOWN_MS`), starts the same recovery session, told to finish the half-done edit in place. Hot reload picks up the fix without a restart.

## Resuming chats

The **resume** button (or `localhost:4747/#resume`) lists every Claude Code chat under `~/.claude/projects`, newest first, searchable by title, first prompt, folder or id. Picking one runs `claude --resume <id>` in the chat's own folder (with `--permission-mode bypassPermissions` unless the checkbox is off / `--safe`). A chat already open in maxflow reattaches instead of starting twice; one held by another claude process (`ps`) is flagged and needs confirming, since two processes on one transcript fork it.

## Running

Installed as a launchd agent (`~/Library/LaunchAgents/com.isaacchacko.maxflow.plist`), so it starts at login and outlives any shell. Restart after edits with `launchctl kickstart -k gui/$(id -u)/com.isaacchacko.maxflow`; logs in `/tmp/maxflow.log`.

The UI is React + shadcn/ui + Tailwind in `src/`, bundled by Bun from the `src/index.html` import in `server.ts` with hot reload, so edits show up without a restart. Bun reads the Tailwind plugin from `bunfig.toml` in its working directory, so the launchd agent runs from this folder.

Bound to loopback only; requests with a foreign `Origin` are refused, so other sites can't drive it.
